# 6.6 first increment: workout preview

Status: development candidate, not a release. Base: 7f33647 (published 6.5).

## Behavior
- Today and Plan open a read-only workout detail view. Strength shows warm-up,
  exercises, sets, repetitions, rest, RIR and current-history weight proposals.
  Endurance shows each segment's duration and effort.
- Today's preview and Train use the same coach proposal and time budget as Today.
  An explicit library choice remains a manual workout. Starting a planned workout
  retains its plan ID; opening or closing a preview never starts a workout.
- Future previews show the planned template without applying today's recovery.
  They explicitly identify contents and weights as provisional. Completed plans
  are labelled as plan previews, not historical execution records.
- Finnish navigation, visible Train details, no stale 6.3 label, larger touch
  controls and wrapping plan cards on narrow screens. This is not a full redesign.

## Validation
- 30/30 Node tests passed, including six new preview/selection regression cases.
- Inline module and service-worker syntax, manifest JSON and diff whitespace checked.
- Tests verify no state mutation during preview, preserving an existing workout,
  future intensity despite today's poor recovery, locked plans, rest-day selection,
  current-day start/preview agreement, HTML escaping and pain-related disabled start.
- Browser visual testing blocked: cloud browser could not reach the local HTTP
  server (ERR_CONNECTION_REFUSED). No claim of mobile visual acceptance is made.
- Before merge: inspect at 375/390/430px, iPad and desktop; open/close previews from
  Today and Plan; verify focus, scrolling, keyboard, timers, offline restart and
  real iPhone PWA. Garmin/Oura live sync was not re-tested in this increment.

## Compatibility, risks and rollback
No manifest identity, /Gym/ path, localStorage keys/schema, OAuth, Worker, sync or
service-worker changes. Preview selection is transient UI state only. No migration.
Future content is a current template estimate, not a frozen future prescription.
Version/cache release preparation is intentionally deferred to an approved release.
If this increment must be rolled back, revert its code commit and deploy the prior
code only after approval. Never restore an old user backup over newer workout data.
No merge or production deployment is authorized by this PR.

## Approved direction after this increment
1. History-based strength and running progression, maintenance, deload and return
   from breaks, using sufficient comparable evidence and short workout feedback.
2. Multi-week blocks and explained split-change suggestions, with explicit approval
   for significant workload/goal/split changes and undo without rewriting history.
3. Review existing exercise-swap implementation before adding anything: 6.5 already
   contains replacement suggestions, search and planned/performed identifiers.
4. Coordinate strength, running and other activities against actual available time.
5. Keep offline coaching deterministic/testable. Any future language-model service
   needs a separately defined data-sharing consent and integration scope.
